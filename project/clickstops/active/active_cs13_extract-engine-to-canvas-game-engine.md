## Background

By CS13 claim, sub-invaders ships `src/engine/` as a 9-module Canvas 2D engine slice (`loop`, `entity`, `collision`, `input`, `renderer`, `sprite`, `audio`, `scene`, `seed`) with full sibling test coverage (119 tests, ~1700 LOC across module + test pairs), enforced one-way isolation from `src/game/` via `scripts/check-engine-isolation.mjs` (fail-closed lint, runs in CI), and a README documenting the extraction contract: `> The future package target placeholder is henrik-me/canvas-game-engine. The engine surface in src/engine/ is the candidate API for that future package, so keep every module game-agnostic.` (`src/engine/README.md:8-10`).

CS02 LOCKED the "engine isolation invariant" as a `CONVENTIONS.md` clause specifically *anticipating* this extraction (`CONVENTIONS.md:180-184`: "Engine code (`src/engine/`) is a candidate for extraction into a separate package. Keep its surface API stable and game-agnostic. The no-reverse-imports rule [...] is repeated here explicitly so it survives a future repo split."). CS13 is the realization of that anticipated future.

**CS13 depends on CS14 (esbuild bundler intro).** Sub-invaders serves `src/` directly to the browser via SWA (`app_location: "src"`); browsers cannot resolve bare-package-name ESM imports (`from 'canvas-game-engine/loop.mjs'`) without either an import map + vendored copy, OR a bundler that resolves and inlines deps at build time. CS14 introduces esbuild for the latter approach; CS13 then consumes the extracted engine through that bundler. CS13 cannot claim until CS14 closes.

**Sequencing rationale (autonomous decision made during R1 review iteration):** The user picked "introduce a bundler" as the blocker resolution, then delegated the sequencing question. The agent autonomously split bundler intro into a separate CS (CS14) rather than jamming it into CS13. Rationale: OPERATIONS.md "Keep PRs small and focused"; bundler intro + engine extraction in one PR pair would touch ~25+ files across build/CI/source/docs/new-repo and a single regression would block both improvements; sequenced CSes let the bundler stabilize through one prod cycle before extraction depends on it; each CS is independently revertible.

## Risks + open questions

1. **R1 — Import specifier shape mismatch.** If `canvas-game-engine`'s `package.json` `exports` map doesn't match the way sub-invaders writes its imports (e.g., trailing `.mjs` extension required vs omitted, or `./` prefix handling), the Phase B import rewrite will fail at runtime even though static analysis passes. Mitigation: in Phase A step 14, the post-merge integration verification uses the exact import shape sub-invaders will use; if it fails there, adjust the `exports` map in a follow-up PR + re-merge BEFORE tagging `v0.1.0`.
2. **R2 — Node-version skew.** Sub-invaders' CI matrix and the new repo's CI matrix must overlap. Sub-invaders currently uses Node 20.x; the new repo specifies `node-version: [20.x, 22.x]` (CS13 deliverable 10). If the engine code accidentally depends on a Node ≥22 feature, sub-invaders breaks. Mitigation: copy verbatim with no edits beyond JSDoc; JSDoc is comment-only and runtime-inert.
3. **R3 — Coverage threshold delta.** Deleting 9 engine test files removes ~119 tests from sub-invaders' `test:unit:coverage` count. If `coverage-thresholds.json` is a percentage gate, this likely *raises* sub-invaders' game-code coverage percentage (engine code is no longer in the denominator). If it's an absolute test-count gate, the delete might trip it. Mitigation: read `coverage-thresholds.json` during Phase B execution; verify both before and after; adjust the threshold if and only if the delta is mechanical-only (not a real regression).
4. **R4 — Harness init shape mismatch for a library repo.** `harness init` was designed for app-shaped consumers (sub-invaders), not library-shaped consumers (`canvas-game-engine`). Likely friction: deploy-related scaffolds being default-on, `health/`, `flags/`, `seeds/` directories being seeded when they're irrelevant. Mitigation (per CS13-17, replacing the R1-era wording that re-introduced the doctrine pitfall sub-invaders#91 exposed): invoke `harness init` with explicit scaffold opt-outs per Phase A step 3; if `init` still emits irrelevant dirs, delete them in the bootstrap PR AND record the friction in this repo's `LEARNINGS.md` (with full reproduction steps) plus a `cs13/agent-harness-followup` entry in WORKBOARD or the active CS13 file's `Notes / Learnings` section. **DO NOT directly file an issue in `henrik-me/agent-harness`** — per OPERATIONS.md § Cross-repo procedures, sub-invaders agents do not file in the harness orchestrator's home; the user reviews the LEARNINGS entry and decides whether to file upstream manually.
5. **R5 — Cross-repo plan review accounting (CORRECTED per R3 finding #2).** REVIEWS.md mandates plan-review attestation for CSes; the rubber-duck pre-merge review for Phase A's bootstrap PR happens *inside the new repo* and attests against the new repo's `project/clickstops/done/done_cs01_bootstrap.md` clickstop file (NOT against the seeded doctrine docs — those never host plan-review tables). The bootstrap PR is self-bootstrapping: the same commit that seeds REVIEWS.md and the clickstops/ structure via `harness init` also commits the bootstrap CS01 clickstop file and is reviewed against the doctrine being installed. This pattern mirrors sub-invaders' own CS01 bootstrap and is the standard new-consumer pattern.
6. **R6 — Tag-then-bootstrap chicken-and-egg.** Phase A step 15 tags `v0.1.0` on the bootstrap merge commit. If Phase B finds an issue with the tagged code that requires an engine-side fix, the fix has to ship as `v0.1.1` (the existing tag is immutable per release doctrine). Mitigation: Phase A step 14's post-merge integration verification catches integration issues before tagging. If a post-tag bug surfaces, file `v0.1.1` immediately and bump Phase B's dep pin.
7. **R7 — Future sub-invaders engine bugfixes require a round-trip.** Once `src/engine/` is deleted, any engine bug found while working on sub-invaders requires: PR to `canvas-game-engine`, merge, tag bump, sub-invaders dep bump. This is by-design (extraction's whole point) but adds latency for hot engine fixes. Mitigation: documented in close-out LEARNINGS as an accepted tradeoff. Hotfix path: temporary `"canvas-game-engine": "github:henrik-me/canvas-game-engine#<branch-name>"` pin during iteration, then re-pin to a tag for merge.
8. **R8 — Engine tests run twice (once upstream, once nowhere in sub-invaders).** Sub-invaders' coverage report loses the engine tests entirely. This is correct (they belong upstream) but means the sub-invaders CI no longer attests engine correctness. Mitigation: the new repo's CI is required-on `main` per its own gates; sub-invaders' `package.json` git-URL dep at a pinned tag is reproducible byte-for-byte. Document the trust delegation in CONVENTIONS.md update (Phase B step 22 — see CS13-15 block (i)).
